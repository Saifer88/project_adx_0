# ADX token benchmark

A reproducible source-reading comparison of equivalent ADX and React UserCard
components and runnable support portals. Selected file sets model tasks; they
are not recordings of what an agent actually reads.

This directory is **dev-only**. It is not part of the published npm package
(`benchmark/` is deliberately absent from `package.json`'s `files` allowlist).

## Run it

```sh
npm run benchmark
```

That compiles `run.ts` to `dist/benchmark/run.js` (via `tsconfig.benchmark.json`,
kept separate from the main build so the published `dist/` layout is untouched)
and runs it. It prints a per-task table naming the encoder used and writes
`benchmark/results.json`.

## What is measured

The default report has `scope: "source-read"`. It does not measure edits,
reasoning, retries, task success or full agent cost. UserCard savings are
13.3-13.8%; the support portal includes both gains and regressions. Neither
fixture predicts full-workflow savings or provides a lower bound.

The tokenizer is [`gpt-tokenizer`](https://www.npmjs.com/package/gpt-tokenizer)
(pure JS, MIT), using the GPT-4o **`o200k_base`** encoder. Each task is a concrete
operation defined by the file set an agent must read to perform it (see
`tasks.json`). The metric is the sum of `encode(file).length` over the selected
set, without file-path/tool-message overhead. Setup, documentation, generated
output, dependencies, and acceptance tests are not included. The portal's shared
build adapter is included equally in its full-read scenario.

| Task | ADX files read | React files read |
| --- | --- | --- |
| `understand` | `manifest.json` + `structure.adx` + `behavior.adx.js` + `style.adx.css` | `UserCard.tsx` + `UserCard.module.css` |
| `modify-style` | `style.adx.css` | `UserCard.module.css` |
| `add-prop` | `manifest.json` + `structure.adx` + `behavior.adx.js` | `UserCard.tsx` |

`savings = (react - adx) / react` per task.

## Layout

```
benchmark/
  tasks.json             # UserCard/portal source tasks and workflow specifications
  adx/                   # a copy of the measured ADX fixture (fixtures/user-card)
  react/                 # a committed, hand-written React equivalent
    UserCard.tsx
    UserCard.module.css
  run.ts                 # pure measure() + the CLI entry
  results.json           # generated by `npm run benchmark`
  app/
    data.json            # shared ticket data, including HTML-like text
    pages.mjs            # shared routes, page data, and workload counts
    style.css            # identical global CSS for both implementations
    build.mjs            # ADX CLI build + React prerendering and hydration bundle
    adx/                 # five reusable ADX components (four files each)
    react/               # equivalent React components and client entry
    dist/                # generated preview output; ignored, not published
```

`adx/` is a copy of `fixtures/user-card`. If that fixture changes, re-copy its
four files here and re-run the benchmark.

## Equivalence

A savings number is only credible if the React fixture is a faithful equivalent
of the ADX fixture. The following parity was checked between `adx/` and `react/`
(a reviewer can confirm with `git diff`):

- **Same DOM and visible text.** Both render an `article.card` containing an
  `img.avatar` (`src`/`alt`), a `div.content` with `h2.name`, `p.role`, and a
  conditional `p.bio` (rendered only when `bio` is non-empty), followed by an
  actions region (the ADX `actions` slot; the React `actions` prop / `div.actions`).
- **Same props, same required/optional/defaults.** `name` is required with no
  default; `avatar` defaults to `/default.png`; `bio` defaults to `""`; `role`
  defaults to `"User"`. The React component declares the identical defaults in its
  destructuring and the identical types in `UserCardProps`.
- **Same styling surface.** `UserCard.module.css` carries the same classes and the
  same rules as `style.adx.css` (`.card`, `.card:hover`, `.avatar`, `.content`,
  `.name`, `.role`, `.bio`, `.actions`). ADX's abbreviated token properties
  (`pad`, `bg`, `radius`, `shadow`, `size`, `weight`) are written as their standard
  CSS equivalents resolved to the same design-token values (e.g. `space-4` = 16px,
  `radius-lg` = 12px, `shadow-md`), so neither side is under- or over-specified.
- **Same events.** ADX emits `click`/`follow`; the React equivalent exposes
  `onClick`/`onFollow` with the same payload shape (`{ name, target }` /
  `{ name }`).

The ADX side is measured as authored source. React is a single `.tsx` plus a CSS
module (no separate `types.ts` is needed — the prop interface lives inline in
`UserCard.tsx`), which is the idiomatic minimal equivalent.

## Runnable application: support portal

The application adds three page types across five working routes:

- `/`: workload counts and recent tickets.
- `/tickets/`: all tickets with reusable rows and status badges.
- `/ticket-1042/`, `/ticket-1043/`, `/ticket-1044/`: customer information,
  priority selection, and an editable response draft.

Drafts validate non-whitespace input and show live success/error feedback.
They are explicitly local to the current page and reset on reload. There is no
backend, authentication, persistence, runtime list insertion, or runtime filtering.
This is a realistic frontend fixture, not a production support service.

```sh
npm ci
npm run benchmark:app
# Preview one implementation at a time; stop with Ctrl+C.
node dist/cli.js serve benchmark/app/dist/adx
node dist/cli.js serve benchmark/app/dist/react
```

Open the printed URL. `npm run benchmark:app` builds both implementations and
can be rerun after edits. Serve each output root separately because shared asset
URLs and navigation are root-absolute. React/React DOM and esbuild are pinned
development dependencies; none are ADX runtime dependencies.

### Equivalence and acceptance

Both implementations use exactly the same data, routes, semantic content, and
CSS. ADX composes header, metrics, list, detail and status-badge components.
React uses corresponding components with state hooks and real prerendered HTML,
then hydrates it; it is not a client-only empty shell. Shared build tooling
adapts the same page models to ADX manifests and React props.

Run the shared executable baseline checks:

```sh
npm run test:browser -- test/browser/benchmark-app.spec.ts
```

The same checks run on both frameworks at 1280px and 390px:
all routes and metadata without JavaScript; matching visible content, links,
control values and row spacing; navigation; initial selected priority and draft;
validation, keyboard save, escaped HTML-like text, cross-ticket isolation and
reload reset; no horizontal overflow, script errors or failed asset requests.
An additional check covers all routes at 375px with 150% text sizing.
They run in CI as part of the existing browser suite.

### Application source-reading results

| Task | ADX tokens | React tokens | Savings |
| --- | ---: | ---: | ---: |
| `portal-understand` | 3,918 | 3,768 | -4.0% |
| `portal-style` | 1,042 | 1,042 | 0.0% |
| `portal-add-field` | 1,035 | 959 | -7.9% |
| `portal-validation` | 227 | 576 | 60.6% |

These are **source-reading** results, not whole-task costs. Negative savings mean
ADX requires more tokens for the chosen files. The complete read counts all
authored framework files plus shared data, page definitions, CSS and build
tooling. Empty component CSS files contribute zero tokens; styling is shared,
not silently omitted. The style task reads that same CSS on both sides and is
intentionally neutral. The field task includes ticket data and detail source.
The validation task assumes the responsible file is already located: ADX reads
its behavior file, React reads the component containing its handlers. A React
implementation with extracted handlers could change that result.
ADX manifest types/required-prop metadata are included in its source totals;
the minimal React JSX fixture does not add a separate runtime prop validator.

Do not average these overlapping scenarios into a headline savings claim.
Shared inputs are counted on each side, but agent discovery, setup, reference
reading, editing and retries still require real workflow recordings.

## Error handling

The benchmark is a dev tool: a missing fixture file or an encoder import failure
throws a plain Node error (not an `[ADX]` compiler error) and fails
`npm run benchmark`.

## Recorded Agent Workflows

The harness can also validate and summarize real paired workflow recordings:

```sh
npm run benchmark -- --workflow /path/to/runs.json
```

This command only analyzes supplied records; it does not invoke an AI provider,
run an agent or fabricate measurements. No real workflow results are included yet.
The report goes to stdout and leaves the source-reading results unchanged.

Use the `workflowTasks` prompts and acceptance criteria in `tasks.json`. UserCard
tasks remain; portal tasks cover locating behavior, cross-page styling, adding an
optional field, reusing components on a new page, stricter draft validation, and
building from a brief. The browser suite proves baseline fixture equivalence;
task-specific changes still need executable checks for their new requirements.
The from-brief task starts without the chosen framework's implementation, using
the same supplied data, CSS and acceptance contract.

Protocol:

1. Fix the model/version, agent instructions, tool availability, starting revision,
  cache policy and maximum attempt/time budgets in a versioned protocol document.
  Apply the same Caveman ultra communication policy to both frameworks, with
  normal prose for persisted code/docs and no loss of important warnings. Do not
  give only ADX a compressed-output policy.
2. Start both frameworks from clean equivalent fixtures. Include framework-specific
  setup/reference material in measured context. Alternate the run order and use
  fresh sessions; retain failed and timed-out runs, not only successes.
  Use the same styling strategy (the portal baseline uses shared plain CSS).
  Keep shared fixtures/build tooling and acceptance tests fixed; framework edits
  must not weaken checks or silently change the other implementation.
3. Record provider-reported input/output totals across all requests, including
  retries and reasoning where counted by the provider. Cached input is a subset
  of input tokens, not an additional token total. Record full wall-clock duration
  and the number of edit/validation attempts.
4. Run the same task acceptance checks for both frameworks. Mark `passed` only
  when all checks pass; retain logs, patches and test output as evidence.
5. Match pairs by task, model and trial using the same protocol. Repeat trials
  before drawing conclusions; report success rate alongside cost and latency.

`runs.json` is a non-empty array of records with these fields:

| Field | Meaning |
| --- | --- |
| `task`, `model`, `trial` | Non-empty strings identifying a paired trial |
| `protocol` | Shared version/revision of the comparison protocol |
| `framework` | `adx` or `react` |
| `inputTokens` | Total input tokens, including cached input |
| `cachedInputTokens` | Cached subset, between zero and inputTokens |
| `outputTokens` | Total provider-reported output tokens |
| `durationMs` | Full elapsed time, including retries |
| `attempts` | Positive integer number of edit/validation attempts |
| `passed` | Boolean result of external acceptance checks |
| `evidence` | Path or reference to retained trace, patch and check results |

Counts must be nonnegative safe integers. Each task/model/trial must have exactly
one ADX and one React record with matching protocol identifiers. The tool validates
record shape and pairing; it cannot independently authenticate logs or acceptance
results. Per-pair savings are null when either run fails or the React token total
is zero. Failed-run costs remain in totals. This is a token comparison, not a
dollar-cost estimate: cached and uncached pricing must be analyzed separately.
